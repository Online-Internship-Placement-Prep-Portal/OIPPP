# Deployment (demo environment)

How to put OIPPP on the free services named in the SRS (2.4, 2.5) and the SAD (3.6): MongoDB Atlas M0, Render, Brevo SMTP and UptimeRobot. The [render.yaml](../../render.yaml) blueprint at the repository root describes both services.

| Piece | Service | Notes |
|:--|:--|:--|
| Database | MongoDB Atlas M0 | A replica set, so aptitude transactions work. 512 MB is enough for about 2,000 resumes at 2 MB each (SAD 3.7) |
| API | Render web service `oippp-api` | Sleeps after 15 minutes idle; the first request then takes about 30 s |
| Client | Render static site `oippp-client` | Built with Vite 8 on Node 22; every path is rewritten to `index.html` |
| Email | Brevo SMTP | 300 emails a day. With `SMTP_HOST` empty, emails are logged instead of sent |
| Monitoring | UptimeRobot | Pings `/api/health` every 5 minutes (SAD 4.4) |

## 1. MongoDB Atlas

1. Create a free M0 cluster in the region nearest Render's (Singapore for India).
2. **Database Access:** add the user `oippp-api` with *Read and write to any database* and a long generated password.
3. **Network Access:** Render's free plan has no fixed outbound IP, so allow `0.0.0.0/0`. The database password is then the only guard, so keep it long and never commit it.
4. **Connect → Drivers:** copy the URI and add the database name, for example `mongodb+srv://oippp-api:<password>@cluster0.xxxxx.mongodb.net/oippp?retryWrites=true&w=majority`.
5. **Backups:** M0 has no automatic snapshots. Before each demo, export with `mongodump --uri "<uri>"` (SRS section 6 assumes daily snapshots, which need a paid tier).

## 2. Brevo SMTP

1. Sign up at brevo.com and verify the sender address you will use in `MAIL_FROM`.
2. **SMTP & API → SMTP:** note the login and generate an SMTP key. The host is `smtp-relay.brevo.com` on port 587 (STARTTLS).

## 3. Render

1. In Render, choose **New → Blueprint**, connect the GitHub repository and pick the `main` branch. Render reads `render.yaml` and proposes both services.
2. Fill in the values marked *sync: false*:

   | Service | Key | Value |
   |:--|:--|:--|
   | oippp-api | `MONGO_URI` | The Atlas URI from step 1 |
   | oippp-api | `CLIENT_ORIGIN` | The client URL, e.g. `https://oippp-client.onrender.com` (CORS allows only this origin) |
   | oippp-api | `SMTP_USER`, `SMTP_PASS` | Brevo login and SMTP key |
   | oippp-api | `MAIL_FROM` | `OIPPP <verified-sender@your-domain>` |
   | oippp-api | `ADMIN_EMAIL`, `ADMIN_PASSWORD` | The first admin account (used only by the seed command below) |
   | oippp-client | `VITE_API_URL` | The API URL plus `/api`, e.g. `https://oippp-api.onrender.com/api`. It is baked in at build time; see the [client README](../../client/README.md) |

   `JWT_SECRET` is generated by Render. `TRUST_PROXY=1` is already set, so rate limits (SEC-5) see each student's real IP behind Render's proxy.
3. Apply the blueprint. Auto-deploy is off. Deploy each service with **Manual Deploy** after `main` is updated.
4. Create the first admin from a laptop, since the free plan has no shell. Run this from `server/`:

   ```bash
   MONGO_URI="<atlas uri>" ADMIN_EMAIL="<email>" ADMIN_PASSWORD="<password>" npm run seed
   ```

   For a demo with sample data, run `npm run seed:demo` the same way. It loads the Test Plan section 6 data set and never touches real student data. Add `--reset` to rebuild it. It deletes all users, listings and applications first, so never run it against a database with real users.
5. Open `https://<api>/api/health`. It should return `{"status":"ok"}`. Then open the client URL and log in as the admin.

## 4. Monitoring (UptimeRobot)

1. Add an **HTTP(s)** monitor for `https://<api>/api/health` every 5 minutes, with an email alert to the team.
2. During demo weeks this also stops the API from sleeping (SAD 3.7). Pause it outside demo weeks to stay within Render's free hours.

## 5. Post-deploy checks

These are the Test Plan checks that only make sense on the deployed URL. Record the results in [the test report](../testing/test-report.md).

| Check | How | Expected |
|:--|:--|:--|
| SEC-2 HTTPS | `curl -I http://<api>/api/health` | `301`/`308` redirect to `https://` (Render forces HTTPS) |
| SEC-2 TLS version | Run https://www.ssllabs.com/ssltest/ on both hostnames | TLS 1.2 and 1.3 only; grade A |
| TC-SEC-02 rate limit | `npm run test:api -- --env-var baseUrl=https://<api>/api --env-var adminEmail=<email> --env-var adminPassword=<password>` | All assertions pass, including the 429 on the 11th login |
| ZAP baseline | Set the repository variable `TARGET_URL` to the client URL, then run the **ZAP baseline scan** workflow | No High findings. Medium and Low go to GitHub issues |
| PERF-1/2/3 | Run `npm run test:load` on the test VM against a build started with `TRUST_PROXY=1` and `seed:demo --students=2000` data, as the Test Plan risk table says. Against Render, all virtual users share your one IP, so the 300 requests/minute API limit applies to all of them together | p95 under 2 s (search), 1 s (other calls), 3 s (dashboard) |

`test:api` and `seed:demo` create test accounts. Run them against a demo database, not one in real use.

Notes:

- The first deploy failed: the API exited with `Cannot find module 'mongodb'`, because `npm ci --omit=dev` leaves out the copy that `mongodb-memory-server` brings in. Logged as #99 and fixed in PR #100.

- `seed:demo --reset` deletes every user, listing and application. Don't run it during the test week; teammates' results depend on this data.
